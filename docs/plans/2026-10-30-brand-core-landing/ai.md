# AI용 계획: 랜딩이 "그냥 GPT 쓰면 되잖아요?"에 답하는가

- 승인: 2026-10-30. 창업자가 "창업자 확인 15분을 지금 하자"고 해서 승인으로 봤고, 정해 줄 것 1~4는 추천안이다. 확인 답으로 기준이 바뀐 곳은 `criteria.md` "창업자 확인 결과"에 있다.
- 1쪽 요약: `docs/plans/2026-10-30-brand-core-landing/human.md`
- 사람이 본 것은 1쪽 요약이고 이 파일이 실행 기준이다.

## 목표와 완료 조건

랜딩(`landing/`)이 반문 "그냥 GPT 앱에서 하면 되는 거 아니에요?"에 답하는지 네 고리(L1~L4)와 브랜드 코어 15개 요소(E1~E15)로 판정하고, 먼저 고칠 곳 3개를 낸다.

완료 조건(모두 충족해야 통과):
1. `out/exposure/*.json`이 3개 경로(`/`, `/v/h2`, `/v/h3`) × 3개 폭(phone 390×844, laptop 1366×768, desktop 1920×1080) = 9개 있고, 각 파일에 첫 화면 캡처와 전체 캡처 경로가 들어 있다.
2. `out/report.md`에 L1~L4와 E1~E15 모두 행이 있고, 행마다 위치, 폭별 노출 정도, 판정, 근거(문장 인용 또는 캡처 파일명)가 있다.
3. 폭마다 첫 화면에서 보이는 고리 수가 적혀 있다.
4. 금지 표현(E15) 검사 결과가 있고, `criteria.md`의 의도된 차이(D1~D4)를 결함으로 센 행이 0개다.
5. 고칠 곳 3개, 각각 근거 2개 이상. "PRD 판단 필요" 목록이 따로 있다.
6. AI 독자 결과는 모두 "가설"로 표시돼 있다.

코드는 바꾸지 않으므로 `gates.mjs`는 대상이 아니다.

## 확인된 사실

- 기준: `docs/plans/2026-10-30-brand-core-landing/criteria.md` (창업자 확인 끝, "확인 뒤 바뀐 기준 문장"이 우선)
- 랜딩 문구 원천: `landing/content/landing.ts`(히어로·문제·전환·차이·시작·신청), `landing/content/loop.ts`(작동 방식 4단계, 히어로 데모), `landing/content/docs.ts`(가이드)
- 히어로 변형: `landing.ts:29-33` `h1` 메인, `h2` "“자격증 있어요” 대신 “이렇게 써 봤어요”", `h3` "자격증 공부하면서 면접 답변도 같이 쌓으세요". 경로 `/v/h2`, `/v/h3`
- 히어로 데모는 768px 미만에서 숨는다(`components/hero/hero-demo.css`). 폰 안내 문구 `landing.ts:36`
- 작동 방식 패널은 선택한 단계만 보인다(`components/loop/LoopStepper.tsx`, `role="tab"`). 리마인드는 "출시 예정 기능"(`loop.ts:489`)
- "다른 점" 섹션은 "지원할 때 쓰는 도구"와만 비교한다(`landing.ts:91-109`)
- GPT 관련 문구: 히어로 sub `landing.ts:34`, 작동 방식 캡션 `landing.ts:86`, 시작 단계 `landing.ts:116`, 요금 띠 `landing.ts:128`
- 데스크톱 v1에서 하지 않는 것: 현장 과제, 면접 답변 화면, 리마인더, 모바일(`docs/desktop/prd.md` §6)
- 랜딩 PRD는 SQLD를 첫 과목·CTA 우선 대상으로 둔다(`landing/Experii_PRD_v0.1.md:85,150`). 데스크톱 PRD는 과목을 사용자가 만든다(`docs/desktop/prd.md` FR-02)
- 경쟁사 이름 검사 정규식 `/\b(TIO|티오|자소설닷컴|jasoseol)\b/i`(`landing/tests/unit/content-guard.test.ts`)는 한글 이름 앞뒤에 `\b`가 서지 않아 한글을 잡지 못한다. E15 검사는 직접 검색으로 한다

## 단계별 작업

산출물 루트: `docs/plans/2026-10-30-brand-core-landing/out/`

### 2. 들어 있나 (먼저 실행)
- 입력: 개발 서버 `http://localhost:3000` (`.claude/launch.json`의 `landing-dev`)
- 할 일: Playwright 스크립트(세션 scratchpad의 `capture.mjs`, `landing/node_modules/playwright` 사용)로 3경로 × 3폭을 연다. 히어로 애니메이션이 자리 잡을 때까지 3초 기다린 뒤 첫 화면·전체 캡처를 찍고, 보이는 텍스트 블록마다 문구, 섹션, 문서 위 y좌표, 첫 화면 안 여부, 숨김 여부를 뽑는다. 작동 방식 탭을 하나씩 눌러 패널 문구를 "탭 안" 노출로 기록한다. `<title>`, og·twitter 메타도 뽑는다
- 산출물: `out/shots/*.png`, `out/exposure/<route>-<vp>.json`
- 검증: 파일 9개, 각 파일의 블록 수 > 0, phone 첫 화면 캡처에 히어로 h1이 있다

### 3. 맞게 말하나 / 4. 반문에 답하나 (2단계 뒤, 서로 병렬)
- 3: 요소별 매퍼가 `criteria.md`와 exposure JSON을 대조해 E1~E15, L1~L4마다 위치·노출 정도·판정을 낸다. 판정마다 반박 검토자가 한 번 더 본다(의도된 차이를 결함으로 세지 않았는지, 탭 안 문장을 첫 화면으로 세지 않았는지). E15는 `landing/content/*.ts` 전체를 직접 검색한다
- 4: 페르소나 3개("GPT로 SQLD 공부 중인 컴공 3학년", "학교 수업을 GPT 프로젝트 폴더로 공부하는 경영학과 4학년", "AI 학습 앱을 의심하는 취준생") × 보기 2개(phone 첫 화면 캡처만, desktop 전체 보이는 텍스트) × 메인 경로. 변형 2개는 phone 첫 화면만 3페르소나. 독자는 기준표를 보지 않는다. 답: 무슨 서비스인지, 누구를 위한지, GPT 앱 대신 쓸 이유, 궁금하거나 믿기지 않는 것. 별도 채점자가 답을 L1~L4와 E1·E3·E9로 채점한다
- 도구: Workflow(에이전트 팬아웃). 결과는 `out/workflow-result.json`

### 5. 판정
- 3·4 결과를 합쳐 `out/report.md`를 쓴다: 요약 3줄, 고리 판정표(폭별 첫 화면 노출 포함), 요소 판정표, 히어로 3안 비교, AI 독자 결과(가설), 정직성 경고, 고칠 곳 3개, PRD 판단 필요
- 사람이 읽을 페이지로 아티팩트도 낸다
- 검증: 완료 조건 1~6을 하나씩 확인한다

## 사람 차례
- 5단계 뒤: 창업자가 `out/report.md`(또는 아티팩트)를 20분 읽고 고칠 곳 중 무엇을 할지 고른다. 고칠 때는 `.claude/rules/ui-change.md`의 시안 3개를 거친다

## 멈춤 조건
- 개발 서버가 뜨지 않거나 페이지 오류로 캡처가 9개 미만이면 멈추고 알린다
- 판정에 기준표에 없는 새 기준이 필요하면(예: 창업자 확인과 다른 해석) 추정하지 않고 묻는다

## 위험과 대응, 범위 밖
- 개발 서버 화면은 배포판과 다를 수 있다(개발용 오버레이). 판정은 문구·배치 기준이라 영향이 작고, 캡처에 오버레이가 보이면 보고서에 적는다
- AI 독자는 사람 반응이 아니다. 가설로만 쓰고, 사람 테스트는 다음 계획으로 넘긴다
- 범위 밖: 랜딩·브랜드 카드·PRD 수정, 배포·측정, 사람 테스트
